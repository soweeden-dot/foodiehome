## 2026-08-08 — Shared Supabase project: Foodie/Keep Track schema isolation

Only two free Supabase projects are available; Foodie will share the existing "Personal" project with Keep Track ("Katie"), which is live and must not be disturbed.

1. **Isolation strategy: dedicated `foodie` Postgres schema**, not table-name prefixing inside `public`. Rationale, full design, and collision analysis in the design-phase turn preceding this entry; final implementation documented in `DATABASE.md` §0 and `ARCHITECTURE.md` §29.
2. **All 33 Foodie tables, 20 enum types, and 14 functions moved from `public` to `foodie`**, in place, in the (never-yet-applied) migration files — not as a new migration, since nothing has been deployed to any real project. This is a pre-deployment rewrite, explicitly not a live-data migration.
3. **The one shared-table touchpoint** (`auth.users` provisioning trigger) is uniquely named (`trg_foodie_new_auth_user`) and calls only `foodie.handle_new_auth_user()`. Keep Track's own trigger(s) on `auth.users`, whatever they are, are neither modified nor assumed to look any particular way — verified by a test harness that simulates a plausible Keep Track footprint (a `profiles` table, a `set_updated_at()` function, an `auth.users` trigger) and asserts it survives Foodie's migrations byte-for-byte unchanged.
4. **`SECURITY DEFINER` functions pin `search_path = foodie, pg_temp`** (previously `public`). One consequence: the invite-code generator was rewritten to derive from `gen_random_uuid()` (core Postgres since PG13) instead of pgcrypto's `gen_random_bytes()`, since the latter's installed schema can no longer be assumed reachable.
5. **No custom Postgres role system introduced for `service_role`.** The project-wide `service_role` key can technically reach `public` (Keep Track) tables regardless of schema isolation — Postgres's RLS bypass isn't schema-scoped. Accepted as a residual shared-project trust cost; mitigated by discipline (minimal, explicitly-scoped `service_role` use) rather than new infrastructure, per explicit instruction not to build one right now.
6. **Manual step required before deployment:** `foodie` must be added to the Supabase project's Exposed Schemas (Project Settings → API) — PostgREST won't serve it otherwise.
7. Storage buckets (none exist yet) and Realtime (not enabled) both get forward-looking documentation notes (`foodie-photos` naming convention; Realtime publication would need `foodie.*` added explicitly later) but no code changes, per explicit scope limits.

## 2026-08-08 — Cleaning + Home Care phase (local-only, freeze still in force)

Built entirely under the live-infrastructure freeze from the entries above — no migration applied to any real project, no Edge Function deployed, no shared Auth0/profile changes, nothing touching `public`/Keep Track/Atlas, no cross-agent writes activated.

1. **Schema:** Stream 1's `recurrence_rules`, `cleaning_tasks`/`cleaning_completions`, and `tracked_components`/`component_replacements` (migrations 03/06/07) were already sufficient in shape — no redesign. Three small additive changes only (migration 15): `cleaning_completions.outcome` (`completed`\|`skipped`, one unified append-only stream instead of a separate skips table — same pattern as `fermentation_logs`), `cleaning_tasks.supplies_needed` (`text[]`), and a new `maintenance_issues` table for the one genuinely new need this phase — a one-off, non-recurring, non-interval apartment issue that fits neither `cleaning_tasks` (needs a recurrence rule) nor `tracked_components` (needs a replace interval).
2. **"Twice weekly: Wednesday + Sunday" needed no schema change.** Modeled as two independent `recurrence_rules` + `cleaning_tasks` rows (one Wednesday-anchored, one Sunday-anchored), each with its own completion/skip history — extending `weekday` to an array was considered and rejected as unnecessary redesign for a single household-level cadence.
3. **Rollover algorithm (interpretive judgment call, documented in code):** next-due = last completion (or the rule's anchor, or today) advanced by one interval, then snapped to the rule's target weekday if set. If that date has already passed and the task is still incomplete, the due date rolls to the nearest upcoming date in the household's fixed cleaning-day set `{Wednesday, Sunday}` — **not** the task's own anchor weekday — so an overdue Wednesday-only task can roll to the coming Sunday instead of waiting a full week. Implemented identically in `supabase/functions/_shared/recurrence.ts` (agent tools) and `app/lib/domain/recurrence.dart` (Flutter UI); next-due is **computed at read time in both places, never stored**, consistent with the "no pre-generated occurrence rows" principle from Stream 1.
4. **Filter/component due dates** are a simpler computation than cleaning — a plain interval in days from the last replacement (or install date), no weekday anchoring, since filters don't follow a household cleaning-day cadence.
5. **SMS/Twilio delivery deliberately not built.** `reminder_event_type` gained `'cleaning_task_due'` (forward-compatible schema only, unused this phase, no worker) so a future combined Katie + Atlas + Foodie morning message can consume due cleaning/filter/maintenance items without a later schema change — per explicit instruction.
6. **Eight new narrow agent tools**, same typed-tool/audited-action architecture as grocery/inventory: `get_cleaning_status`, `complete_cleaning_task`, `skip_cleaning_task`, `get_filter_status`, `log_filter_replacement`, `get_maintenance_issues`, `report_maintenance_issue`, `resolve_maintenance_issue`. All mutating writes go through SECURITY INVOKER RPCs stamping `app.action_source='foodie'`, continuing the `P000x` error-code sequence.
7. **UI:** two screens filled in at the two routes already reserved in Stream 4 (`/home-care` → cleaning + maintenance tabs; `/supplies` → tracked components/filters), following the Inventory phase's gateway/controller/screen pattern exactly. No UI for creating cleaning tasks or tracked components themselves — this phase covers acting on tasks that already exist (complete/skip/replace/report/resolve), not authoring them; household_supplies (consumables) management UI is also deferred, since it wasn't part of this phase's explicit scope.
8. Verified entirely offline/locally: DB harness (6 suites, including the coexistence test — table count 33→34, function leak-list extended), 48 Deno tests (9 new for `recurrence.ts`, plus new tool-validation and orchestrator scenarios), 60 Flutter tests (9 new for `recurrence.dart`, plus new controller and screen tests); both analyzers clean.

## 2026-08-08 — Fermentation Tracking phase (local-only, freeze still in force)

Built entirely under the live-infrastructure freeze from the entries above — no migration applied to any real project, no Edge Function deployed, no shared Auth0/profile changes, nothing touching `public`/Keep Track/Atlas, no cross-agent writes activated.

1. **Schema:** Stream 1's `fermentation_projects`/`fermentation_logs`/`fermentation_photos` (migration 05) were already sufficient in shape — no redesign, no new tables, no new columns. Migration 16 adds only 4 write RPCs. Sourdough and cacao specialization both sit entirely on the existing `project_type` (free text) + `log_type` (enum, already covering observation/feeding/turning/temperature/stage_change/ai_observation) + jsonb `target_params`/`payload` conventions — proof the generic model doesn't force sourdough's shape onto other fermentation types, since cacao needed zero schema accommodation at all.
2. **Sourdough's raw-vs-computed split**, mirroring the cleaning-due-date precedent: a feeding log stores only the raw grams (`starter_g`, `flour_g`, `water_g`, `flour_type`, `discard_g`); hydration %, the starter:flour:water ratio, and next-feed-due are all **computed at read time**, never stored, so a derived value can never drift from the numbers it came from. New `supabase/functions/_shared/sourdough.ts` / `app/lib/domain/sourdough.dart` pure modules, same formulas. Sourdough state (active/refrigerated) and feed cadence live in `target_params` jsonb, not new columns.
3. **`foodie_update_fermentation_stage` records a `stage_change` log entry automatically** on every stage/status change, capturing from→to. This gives "stage history" for free from the existing append-only log stream rather than a separate history table, and setting `status` to `completed`/`discarded` sets `ended_at` — satisfying "completion/archive status" with no new mechanism.
4. **Photos deliberately not built this phase.** `fermentation_photos.storage_path` points at Supabase Storage, and no bucket exists yet — creating one would itself be a live-infrastructure change blocked by the freeze. The schema stays as designed in Stream 1; no capture/upload UI was added, and this is recorded as a real scope limit, not silently skipped.
5. **Five narrow agent tools requested, four built** (`get_cleaning_status`-style parity with the other phases): `get_fermentation_projects`, `get_fermentation_project`, `log_fermentation_event`, `log_sourdough_feeding`, `update_fermentation_stage`. Project *creation* (`foodie_create_fermentation_project`) exists as an RPC (the UI's "start a project" write path) but is deliberately **not** registered as an agent tool — starting a new fermentation project is a UI-only action this phase, distinct from acting on one that already exists.
6. **Recipe interoperability architecture decided and recorded, nothing built.** Atlas will eventually own recipe creation/editing; Foodie reads and understands recipes for cooking, inventory, grocery, scaling, substitutions, and guided cooking, but must never silently modify a master recipe — any future Foodie-initiated recipe change must be explicit and version-safe (a Foodie-local variant, or an explicit user-confirmed versioned write back to Atlas). The future touchpoint (`external_recipe_id`/`external_source`/`external_version` on `foodie.recipes`) is designed and documented in `docs/INTEROP.md`, not migrated in — `foodie.recipes` continues to serve only Foodie-local recipes until Atlas integration is its own explicitly scoped, approved stream.
7. **UI:** a project list screen (`/fermentation`, already reserved in Stream 4) with a "start project" flow, and a project detail screen with sourdough feeding logging (with computed hydration/ratio/next-feed-due display), generic event logging (observation/turning/temperature), stage/status updates, and full log history — following the Inventory/Home-Care phases' gateway/controller/screen pattern exactly.
8. ## 2026-08-08 — Standing architecture decision: Foodie must not depend on paid Anthropic credits by default

Recorded now, ahead of any implementation, because it constrains every future stream touching the model layer:

**Foodie must not depend on paid Anthropic API credits as its default AI provider.** The user's plan is an optional AI bridge running on their own laptop; every Foodie app must remain fully functional when that bridge is unavailable. Consequences, binding on all future work:

1. **Deterministic Foodie features must never require an AI call.** This was already true by construction for every domain built so far (grocery, inventory, cleaning/home-care, fermentation) — none of their read/write paths touch `ModelProvider`. The Home Dashboard phase (below) is the first place this constraint is explicitly tested and asserted, not just incidentally true.
2. **The dashboard specifically must use zero model calls.** `domain/dashboard.dart`'s `aggregateDashboard` is a pure function; `dashboard_controller_test.dart` proves this concretely by constructing a `ProviderContainer` with every domain gateway faked but **no** `FoodieGateway`/AI provider override — if the dashboard ever touched one, the test would fail loudly rather than silently passing.
3. **`ANTHROPIC_API_KEY` is not deployed or activated.** Already true under the live-infrastructure freeze (no Edge Function deployment), and recorded here as a standing rule independent of the freeze too — this isn't only a "not yet," it's "not as the permanent default."
4. **The `ModelProvider` abstraction (`supabase/functions/_shared/types.ts`, implemented by `anthropic_provider.ts`) stays the intended seam for a future laptop-bridge provider.** No orchestrator/tool/context change is anticipated when that bridge lands — only a new `ModelProvider` implementation, exactly like any other provider swap. See `docs/FOODIE.md`'s Provider boundary section.
5. **Foodie is not coupled to Anthropic as the permanent provider.** Anthropic is today's implementation choice behind a replaceable boundary, not an assumed constant elsewhere in the architecture.

The laptop bridge itself is **not implemented this phase or any prior one** — this entry records the constraint so future work is built toward it, per the same "record the decision now, build later" pattern as the recipe-interoperability entry above.

## 2026-08-08 — Home Dashboard / Kitchen Command Center phase (local-only, freeze still in force)

Verified entirely offline/locally: DB harness (7 suites — unchanged, no schema touched this phase), 65 Deno tests (unchanged, no Edge Function code touched this phase), 96 Flutter tests (17 new: 9 for `aggregateDashboard`'s due/overdue/expiring/empty-state logic, 4 for `DashboardController`'s composition — including the "zero AI dependency" proof, 6 for the dashboard screen's kitchen/phone layouts, empty states, and quick actions); both analyzers clean.
